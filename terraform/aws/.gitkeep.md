# terraform/aws

**`guardrails/` exists and is applied first.** One resource: the $5 monthly budget alarm ADR-0003
Decision 3 requires to be in place *before* the first AWS resource. `make aws-guardrails` applies
it, `make aws-guardrails-verify` reads it back out of the API.

**The cluster state does not exist yet**, and that is the point of the split. `terraform apply`
creates in dependency order and nothing would order a budget before a node group, so the guardrail
lives in a state of its own that `make aws-down` never destroys (ADR-0022 Decision 1).

What arrives with the cluster, in the same change as the `aws-up` target that will refuse to run
without a verified alarm:

- the VPC, two public subnets across two AZs (EKS requires two; the nodes are pinned to the first)
- the EKS cluster and one `m6a.large` spot node group — **not `t3.*`**, which is burstable and
  would repeat Module 08's silent `Insufficient cpu` failure
- IRSA for External Secrets, the AWS answer to Workload Identity

See `docs/adr/0022-aws-guardrail.md` and `clusters/aws/cluster.json`.
