| 2026-10-26 | **`make onprem-vms` can never report "No changes" after a host restart.** Every run plans `6 to add, 3 to change, 3 to destroy`: the three `libvirt_cloudinit_disk` resources read as absent and are recreated, which forces replacement of the three seed volumes whose `create.content.url` points at them. The cause is where the provider puts the generated ISO — `/tmp/terraform-provider-libvirt-cloudinit/cloudinit-<id>.iso` — which does not survive a restart, so Read() finds nothing and reports the resource gone. | It is noise, not damage, and the thing that makes it safe is worth knowing: `meta_data.instance-id` is derived deterministically (`k8s-cp01-7f48b5b8` is the same on every run), and cloud-init only re-runs when the instance-id changes. Read the plan, check that the only changes are the three cloudinit disks and the three seed volumes, and apply. **Sharpened 2026-10-27:** it is not every run. Restarting a single node planned `0 to add, 1 to change` - just `running: false -> true` - with no cloudinit churn at all. The ISO lives in `/tmp`, so the noise appears only after something clears it, i.e. a WSL restart. Revisit if Layer 0 ever drifts in a way this masks, or in the cloud modules when the same discipline has to hold against a real provider. |
