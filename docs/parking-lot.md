# Parking lot

Problems deliberately deferred. Rule 2 of the roadmap: if a side problem has eaten 45 minutes, it
lands here and we route around it. Revisit when it blocks something real, not when it annoys you.

| Date | Problem | Why deferred | Workaround in use |
|:--|:--|:--|:--|
| 2026-10-22 | **Hubble Relay runs without TLS.** The chart warns about it on install: `hubble.relay.tls.server.enabled=false`, so flow data between the agents and the relay is unencrypted. | Enabling it means certificate management, and we have not decided how certificates are issued in this cluster yet — that is cert-manager's job, which arrives as a Layer 3 component. Doing it by hand now would create exactly the hand-made thing ADR-0002 Rule 3 exists to prevent. | Nothing. The cluster is on an isolated NAT network inside one laptop, and the only consumer of Hubble is `hubble observe` on the node. **Revisit in Module 10** when the Hubble UI is installed via Argo CD and the flow data leaves the node — and strictly before anything resembling real traffic exists. |
| 2026-10-24 | **kubelet serving certificates are self-signed**, so metrics-server scrapes fail TLS verification and every node reports as unavailable, with an x509 error that reads like a cluster-wide certificate problem. | The clean fix is `serverTLSBootstrap: true` in the KubeletConfiguration, which makes each kubelet request a serving certificate from the cluster CA. kubeadm does not auto-approve those CSRs, so it needs a signing controller — a whole component, for one scrape path, on a lab cluster. | `--kubelet-insecure-tls` on metrics-server only, in `gitops/environments/onprem/metrics-server.yaml`, where it is visibly on-prem-specific rather than hidden in the chart. **Revisit in Module 05's cert-manager work** — once there is a PKI and an approving controller in the cluster, the honest fix costs a values change instead of a new component. |
| 2026-10-24 | **The aggregation layer does not verify metrics-server's certificate either.** The chart sets `insecureSkipTLSVerify: true` on the `v1beta1.metrics.k8s.io` APIService, so the API server accepts whatever metrics-server presents. A second unverified hop, distinct from the kubelet one above: this is API server → metrics-server, that one is metrics-server → kubelet. | Same root cause, same fix: there is no PKI in this cluster yet, so metrics-server self-signs its serving certificate. It is the chart's default for exactly that reason. | Nothing — the chart default stands. **Both hops get fixed together** once cert-manager exists and can issue a serving certificate metrics-server presents and the API server trusts. Doing one without the other would be security theatre: an encrypted-but-unverified hop either side of a verified one. |
| 2026-10-26 | **`make onprem-vms` can never report "No changes" after a host restart.** Every run plans `6 to add, 3 to change, 3 to destroy`: the three `libvirt_cloudinit_disk` resources read as absent and are recreated, which forces replacement of the three seed volumes whose `create.content.url` points at them. The cause is where the provider puts the generated ISO — `/tmp/terraform-provider-libvirt-cloudinit/cloudinit-<id>.iso` — which does not survive a restart, so Read() finds nothing and reports the resource gone. | It is noise, not damage, and the thing that makes it safe is worth knowing: `meta_data.instance-id` is derived deterministically (`k8s-cp01-7f48b5b8` is the same on every run), and cloud-init only re-runs when the instance-id changes. So the seed is rebuilt byte-identical, re-attached, and ignored on the next boot. Fixing it properly means not using the provider's cloudinit resource at all — generating the ISO ourselves into the libvirt pool with `genisoimage`, so its existence is a fact about the pool rather than about `/tmp`. | Nothing. Read the plan, check that the only changes are the three cloudinit disks and the three seed volumes, and apply. **It costs the Layer 0 idempotency check**, which is the real price: `make onprem-vms` reporting changes no longer means anything, so a genuine drift in the domains would hide inside the expected noise. Revisit if Layer 0 ever drifts in a way this masks, or in the cloud modules when the same discipline has to hold against a real provider. |
| 2026-10-26 | **The Argo CD seam applied itself once with nothing in Git having changed.** `argocd : Apply the seam` reported `changed` for `root-onprem.yaml` on a run where no commit had touched that file. The `kubectl diff --server-side` gate ahead of it exists to make that impossible. | It has not reproduced: the next two runs skipped the apply with both diffs returning 0, so there is nothing to debug against. Guessing at a mechanism - a sync in flight, a field-ownership change, the controller's transient `operation` field - would produce a confident-sounding note and no knowledge. | Nothing. The apply is a no-op when it fires, so the only cost is that `changed=0` is slightly less trustworthy than it reads. **Watch for a second occurrence**, and if it comes, capture `kubectl get application platform-onprem -o yaml` and the diff output in the same moment - without both, the next sighting will be as uninformative as this one. |
