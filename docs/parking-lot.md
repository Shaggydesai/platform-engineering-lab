# Parking lot

Problems deliberately deferred. Rule 2 of the roadmap: if a side problem has eaten 45 minutes, it
lands here and we route around it. Revisit when it blocks something real, not when it annoys you.

| Date | Problem | Why deferred | Workaround in use |
|:--|:--|:--|:--|
| 2026-10-22 | **Hubble Relay runs without TLS.** The chart warns about it on install: `hubble.relay.tls.server.enabled=false`, so flow data between the agents and the relay is unencrypted. | Enabling it means certificate management, and we have not decided how certificates are issued in this cluster yet — that is cert-manager's job, which arrives as a Layer 3 component. Doing it by hand now would create exactly the hand-made thing ADR-0002 Rule 3 exists to prevent. | Nothing. The cluster is on an isolated NAT network inside one laptop, and the only consumer of Hubble is `hubble observe` on the node. **Revisit in Module 10** when the Hubble UI is installed via Argo CD and the flow data leaves the node — and strictly before anything resembling real traffic exists. |
| 2026-10-24 | **kubelet serving certificates are self-signed**, so metrics-server scrapes fail TLS verification and every node reports as unavailable, with an x509 error that reads like a cluster-wide certificate problem. | The clean fix is `serverTLSBootstrap: true` in the KubeletConfiguration, which makes each kubelet request a serving certificate from the cluster CA. kubeadm does not auto-approve those CSRs, so it needs a signing controller — a whole component, for one scrape path, on a lab cluster. | `--kubelet-insecure-tls` on metrics-server only, in `gitops/environments/onprem/metrics-server.yaml`, where it is visibly on-prem-specific rather than hidden in the chart. **Revisit in Module 05's cert-manager work** — once there is a PKI and an approving controller in the cluster, the honest fix costs a values change instead of a new component. |
| 2026-10-24 | **The aggregation layer does not verify metrics-server's certificate either.** The chart sets `insecureSkipTLSVerify: true` on the `v1beta1.metrics.k8s.io` APIService, so the API server accepts whatever metrics-server presents. A second unverified hop, distinct from the kubelet one above: this is API server → metrics-server, that one is metrics-server → kubelet. | Same root cause, same fix: there is no PKI in this cluster yet, so metrics-server self-signs its serving certificate. It is the chart's default for exactly that reason. | Nothing — the chart default stands. **Both hops get fixed together** once cert-manager exists and can issue a serving certificate metrics-server presents and the API server trusts. Doing one without the other would be security theatre: an encrypted-but-unverified hop either side of a verified one. |
| 2026-10-26 | **`make onprem-vms` can never report "No changes" after a host restart.** Every run plans `6 to add, 3 to change, 3 to destroy`: the three `libvirt_cloudinit_disk` resources read as absent and are recreated, which forces replacement of the three seed volumes whose `create.content.url` points at them. The cause is where the provider puts the generated ISO — `/tmp/terraform-provider-libvirt-cloudinit/cloudinit-<id>.iso` — which does not survive a restart, so Read() finds nothing and reports the resource gone. | It is noise, not damage, and the thing that makes it safe is worth knowing: `meta_data.instance-id` is derived deterministically (`k8s-cp01-7f48b5b8` is the same on every run), and cloud-init only re-runs when the instance-id changes. So the seed is rebuilt byte-identical, re-attached, and ignored on the next boot. Fixing it properly means not using the provider's cloudinit resource at all — generating the ISO ourselves into the libvirt pool with `genisoimage`, so its existence is a fact about the pool rather than about `/tmp`. | Nothing. Read the plan, check that the only changes are the three cloudinit disks and the three seed volumes, and apply. **Sharpened 2026-10-27:** it is not every run. Restarting a single node planned `0 to add, 1 to change` - just `running: false -> true` - with no cloudinit churn at all. The ISO lives in `/tmp`, so the noise appears only after something clears it, i.e. a WSL restart. That makes the Layer 0 idempotency check usable within a session and unusable across one. **It costs the Layer 0 idempotency check**, which is the real price: `make onprem-vms` reporting changes no longer means anything, so a genuine drift in the domains would hide inside the expected noise. Revisit if Layer 0 ever drifts in a way this masks, or in the cloud modules when the same discipline has to hold against a real provider. |
| 2026-10-26, again 2026-10-29 | **The Argo CD seam re-applies `root-onprem.yaml` with nothing in Git having changed.** Both occurrences were the FIRST run after the cluster was restarted - once after the VMs were stopped and started, once after a WSL restart. Every run in between skipped the apply with `kubectl diff --server-side` returning 0. So it is neither random nor drift from a commit. | Still unexplained, but now a pattern rather than a single sighting. The likely shape is something Argo CD's controller writes to the live object that does not survive, or is rewritten after, a control-plane restart - but naming a field without having seen the diff would be a guess dressed as a cause. | **The role captures it now instead of asking a human to remember.** When a seam object differs, `argocd : Record WHAT differs` writes the diff to `.cache/seam-diff-<file>-<stamp>.diff` and prints it, because the apply three tasks later erases the evidence in the same run. **After the next cluster restart, read that file.** The apply is a no-op, so the only cost remains that `changed=0` reads as more trustworthy than it is. |
| 2026-10-29 | **A `python3 - <<PY ... PY && git commit` chain committed after the python failed.** The heredoc raised `ValueError: substring not found`, the intended edit never happened, and the `&&` only guarded the commands after it - so `lint` passed, the commit ran, and the push succeeded with the file unchanged. | Nothing to defer, really: this is the `--syntax-check \| tail -2` bug from Module 03 in a new shape. Both times a non-zero exit was swallowed by the shape of the command line rather than by any logic. | **Edits that must happen are asserted in the edit itself** - the `assert s.count(old) == 1` that failed here did its job - but the COMMIT must not be chained behind an edit in one line. Separate the calls, or check `git status` before committing. Recorded here rather than fixed in code because the fix is a habit, not a script, and the habit is: a commit is its own step. |
